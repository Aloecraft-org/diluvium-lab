## 1. The homepage Prism grammar is missing the regex literal

**Open. Needs a decision about who does it.**

The backtick literal shipped in `5.5.1_build13` on 2026-09-06. Three
grammars describe this language, and they do not agree about it:

| grammar | repo | backtick regex | format spec |
|---|---|---|---|
| `src/notebook/highlight.js` | diluvium-lab | fixed on this branch | fixed on this branch |
| `site/static/assets/prism-diluvium.js` | diluvium | **missing** | has it |
| `editors/vscode/syntaxes/dlua.tmLanguage.json` | diluvium | has it | has it |

So the public site currently paints `` `(\d+)-(\d+)` `` as an operator,
an identifier and an operator, for a form the compiler has had since
build13. The vscode grammar already got it right, which makes this a
transcription rather than a design question: `string.regexp.dlua` in the
tmLanguage has the three rules that matter — a backtick opens, a doubled
backtick is one backtick of pattern and does not close, and the literal
may not cross a line — and Prism needs the same three as one
`insertBefore('lua', 'string')` entry.

Section 6 gives session C "the lab and the site", so this is C's work by
the plan. It is not blocked; it is out of reach. This session has
read-only access to `Aloecraft-org/diluvium`.

**What would settle it:** push access to `Aloecraft-org/diluvium` for a
session working section 6, or a hand-off to session A, who is already in
that repository. Either is fine. Leaving it is the bad option, because
the mis-colouring is on a public page.

## 2. The two specs — closed

**Received 2026-09-08. Both are now drafted against.**

`diluvium-syntax-proposals.md` and `diluvium-numeric-spec.md` were in
neither repository, so C0's first pass was drafted from what section 4
names plus the language that had already shipped. With the specs in hand,
C0 covers every form in the proposals doc that a *tokenizer can see*:

| form | proposals § | tier | how it is recognised |
|---|---|---|---|
| compound assignment | 3.1 | A | `compound` |
| null-safe `?.` `?[` `??` | 3.4 | A | `optional` |
| null-safe `?:` `?(` | 3.4 | A | `optional-call`, a separate flag — build10 has the first four and not these two |
| separators, `0b` | 3.5 | A | `separators`, `binary` |
| spread `...args` | 3.7 | A | `spread`, told apart from vararg by the name after it |
| literal suffix `0.05d` | 2 | shipped? | `suffix` — see the note below |
| `continue`, `const` | 3.3, 3.6 | A | contextual keyword probes |
| lambdas `\|x\| expr` | 4.1 | B | `lambda` |
| `export` | 4.5 | B | contextual keyword probe |
| attributes `<deterministic>` | 4.6 | B | `attribute`, only after a `)` |
| `class` | 5.1 | C | contextual keyword probe |
| `@` for `self` | 5.1, 8 | C | `at-self` |
| regex literal | shipped build13 | — | `regex` |
| f-string format spec | shipped | — | unconditional |

Deliberately still not drafted, with the reason:

- **Slicing `xs[2:5]`** (4.4). The `:` has to be told apart from a method
  call by bracket depth, which this scanner does not track. Colour value
  is low — the brackets and the colon are already operators — and the
  cost is real. Worth revisiting only if it reads badly once A lands it.
- **Destructuring** (4.2), **`if`/`switch` expressions** (4.3),
  **default parameters** (3.2), **expression-bodied functions** (3.8).
  None introduces a token. `local {host, port} = cfg` is braces and
  identifiers whichever way it is parsed, and there is nothing for a
  tokenizer to colour differently.
- **`extends`, `static`, `super`** (5.1). Special only inside a class
  body, and this tokenizer has no notion of being inside one, so adding
  them would colour them everywhere. The same compromise was already
  accepted for `switch`, but these three sit one construct deeper.
- **Tier D** (6.1 to 6.5). Plan §1 puts it out of scope this round.
- **`~~=`** (3.1). The doc leaves xor-assign undecided — "use `~~=` for
  bitwise-xor-assign or skip xor" — so there is nothing to draft to.

**Checked against A's freeness corpus, 2026-09-09.** A's
`test/syntax/freeness/` now holds 25 files, one per landed form, each a
program stock Lua refuses and Diluvium accepts — the same artifact as
`SYNTAX_CANDIDATES` written from the other side. Diffing them form by
form is the verification available without a build, and it found:

- The notations agree everywhere this repository covers a form.
- **`@` is not class-only.** `28-at-self.lua` reaches it through an
  ordinary `function counter:bump()`. The probe here wrapped it in a
  `class`, needlessly requiring two things to be true. Fixed.
- **`class` was probed with an empty body**, which nothing in A's corpus
  exercises. It has a field now. Fixed.
- **No `?:`/`?(` file**, so the two-flag split was right.
- **No literal-suffix file**, which settles the disagreement below in
  `doc/Guide.md`'s favour: `1.23d` does not exist.
- Slicing, `extends`, `static` and `super` landed, and A's Status asks
  for them by name. All four are now covered; see the ROADMAP for the
  method-call carve-out slicing needs.
- **`case` and `default` were already in build10** and the Lab was
  painting them as identifiers. Giving the body-only keywords snippets
  turned that up; the keyword count moves 26 → 28.
- **`<deterministic>` did not land**, and A's reason is worth keeping:
  the determinism verdict it would consult is specified and unbuilt, so
  an attribute wired today would accept every function, and "a marker
  asserting a property nothing checks reports a falsehood". The form
  stays drafted and dark here, which costs nothing and lights up free.

**Two things in the specs that session A may want to look at:**

- **§2 lists the literal-suffix registry as shipped; `doc/Guide.md` says
  it is not.** Guide line 979: "Ext `0x01` is reserved for decQuad and
  unimplemented, so `1.23d`-style literals do not exist and money is not
  a solved problem here yet." The Lab does not take a side — `suffix` is
  a probe like the rest, and it reports absent on build10 — but one of
  the two documents is wrong and the numeric spec's `0d` examples (§5,
  Stage 0) depend on which.
- **§3.1's operator list reads `... &= |= ~= << >>`.** `~=` is
  not-equal, which the doc itself flags; `<<` and `>>` without a
  following `=` look like a typo for `<<=` and `>>=`. The Lab implements
  `<<=` and `>>=` and does not implement `~=`-as-assignment, which is
  the only reading that is not already a Lua operator.

## Version namespaces, and what this branch did to them

Recorded because three repositories are versioning independently this
sprint and a reconciliation is expected at the end of it. **This branch
changes none of these numbers.** No bump, no pin move, no tag — §0.3
forbids the last two outright, and the rest were not needed.

| number | where it lives | who owns it | value now |
|---|---|---|---|
| Lab version | `package.json` + `src/version.js` | this repo | `0.12.0` |
| Diluvium release | git tags `v5.5.1_buildN` | diluvium | `build13` latest |
| the pin | `vendor/PINNED_TAG`, `vendor/pinned.js`, `vendor/BUILDINFO.txt` | this repo | `v5.5.1_build10` |
| Lua base | `_VERSION` | upstream | `diluvium (lua) 5.5` |
| bytecode format | dump header | diluvium | `0x46` |
| DRT release | `CHANGELOG.yaml` | diluvium-drt | `0.6.0`, unreleased |
| `dv_abi` | `dv.h` | diluvium | `1`, moving to `2` this round (plan §3.1) |

Three things to know before deciding what "sync them up" means:

1. **`src/version.js` argues against it, at length and on purpose.** Its
   header says the Lab's number is the Lab's own, does not track
   Diluvium's, and that pinning one to the other would mean either lying
   about one of them or being unable to ship a fix. Which Diluvium is
   bundled is recorded separately, in `vendor/pinned.js`, and shown
   beside the Lab version in the About panel. Read that comment before
   reconciling — it is a decision, not an accident.
2. **Diluvium's tags carry suffixes because the repository also holds
   upstream Lua's tags.** A bare `v5.4.7` there is Lua's, not
   Diluvium's. Any scheme that drops `_buildN` collides with upstream.
3. **`scripts/check-version.mjs` enforces that `package.json` and
   `src/version.js` agree and that the value is semver.** A scheme that
   is not semver fails that check, which runs in `npm run release`.

Nothing here needs deciding now. It is written down so the decision has
the facts in front of it.

## Also, for session A: the freeness corpus and the probe list are one list

**No decision needed here — this is a note into §3, if the owner agrees
it belongs there.**

§3.6 of the plan has session A building `test/syntax/freeness/*.lua`: one
file per new form, each of which must **fail** to parse on pristine
upstream `luac`. §1 of the proposals doc states the same rule from the
other side. `SYNTAX_CANDIDATES` in `src/kernel/lua-harness.js` is that
same artifact pointed the other way — one snippet per form that parses on
Diluvium and not on stock Lua.

Two lists with the same content and no interface between them drift, and
the drift is silent in both directions: a form A lands with a slightly
different notation leaves the Lab's probe failing forever and nothing
says so.

What the Lab probes today, for A to diff against the corpus:

```
regex          return `x`
separators     return 1_0
binary         return 0b1
suffix         return 1.23d
optional       local a = nil local b = a?.x local c = a?[1] local d = a ?? 1
optional-call  local a = nil local b = a?:m() local c = a?(1)
compound       local a = 1 a += 1
secure         ~function __probe() end
spread         local a = {} local t = {...a}
lambda         local f = |x| x * 2
attribute      function __probe() <deterministic> end
at-self        local t = { n = 0 } function t:bump() @n = @n + 1 return @n end
slice          local xs = {1, 2, 3} return xs[2:3], xs[2:], xs[:2]
continue       for i = 1, 3 do if i == 2 then continue end end   (keyword)
const          const RATE = 1                                    (keyword)
export         export function f() end                           (keyword)
class          class C / x = 0 / end                             (keyword)
extends        local P = {} class C extends P / x = 0 / end      (keyword)
static         class C / static function f() end / end           (keyword)
super          class C / function new() super() end / end        (keyword)
case, default  a switch body with both arms                      (keyword)
```

(`/` stands for a newline in the four-line snippets above.)

If A publishes the corpus in a shape the Lab can read — the files
themselves, or the form names beside them — the Lab reads it and this
list stops being maintained by hand. A is the authoritative side; C
should follow, not duplicate.
